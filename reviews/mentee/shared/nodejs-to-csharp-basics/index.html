01 / TYPE INFERENCE5 min · Session 1

Same variable, new type?

The compiler can infer a type without making the variable dynamically typed.

Node.js / JavaScript
let count = 3;
count = "three";

console.log(count);
C#
var count = 3;
count = "three";

Console.WriteLine(count);
Predict

Which snippet runs? At what stage does the other one fail?

Try a change → Keep the C# variable numeric and print Count: 3 using string interpolation.

Give me a hint

What type does the initial value 3 have? Interpolation changes the output string; it does not need to change that variable's type.

Reveal the explanation

JavaScript: three · C#: compilation error

C# infers int from the initializer. Assigning a string to that variable is rejected before execution. var is compile-time type inference, not the equivalent of JavaScript's let or C#'s dynamic.

Explain it back: why can two C# variables both use var and still have different fixed types?

Understand the inferred type before choosing how to format the output.

02 / INPUT & PARSING5–8 min · Session 1

A number—or just a numeric prefix?

Converting input and validating a business rule are separate decisions.

Node.js / JavaScript
const input = "12cats";
const quantity = Number.parseInt(input, 10);

console.log(quantity);
C#
string input = "12cats";

if (int.TryParse(input, out int quantity))
    Console.WriteLine(quantity);
else
    Console.WriteLine("Invalid number");
Predict

Does either snippet accept this input? Does parsing -2 successfully mean it is an acceptable quantity?

Try a change → Compare "12", "", "-2" and "12.5". Write down the conversion result separately from your validation decision.

Give me a hint

JavaScript's parseInt can stop after reading a valid numeric prefix. C# TryParse returns a Boolean and supplies its numeric result through out.

Reveal the explanation

JavaScript: 12 · C#: Invalid number

For the other inputs, JavaScript produces 12, NaN, -2, 12. The C# integer parse succeeds for "12" and "-2", and fails for the empty string and "12.5". These parsing methods are useful, but their acceptance rules are different.

A successfully parsed integer can still violate a range or business rule. Consider why ordinary invalid user input usually needs a validation response rather than an exception.

Want to go deeper?

Compare conversion behavior first, then decide which inputs the operation should accept.

03 / NULLABILITY5–8 min · Session 1

Missing is not the same as empty.

Null-safe access looks familiar. C# also lets you describe missing values in the type.

Node.js / JavaScript
const nickname = null;

console.log(
  nickname?.toUpperCase() ?? "Guest"
);
C#
#nullable enable
string? nickname = null;

Console.WriteLine(
    nickname?.ToUpperInvariant() ?? "Guest"
);
Predict

What does each print now? What changes if the value becomes ""?

Try a change → Make null, empty and whitespace-only input all display Guest. Keep the original value available.

Give me a hint

?? is not an empty-string check. In C#, investigate string.IsNullOrWhiteSpace; in JavaScript, consider a null-safe trim before checking length.

Reveal the explanation

Both: Guest · With an empty string: a blank line

C# string? expresses that null is possible. With nullable analysis enabled, dereferencing a potentially null value can produce a compiler warning. The annotation does not create runtime validation or prevent all nulls.

The null-forgiving operator ! suppresses a warning; it does not supply a missing value or perform a runtime check. JavaScript also has undefined, which the shown ?? expression handles.

04 / SHARED REFERENCES5 min · Session 1

Two names. One collection.

Some behaviors transfer directly from JavaScript to C#.

Node.js / JavaScript
const names = ["Ada", "Lin"];
const otherNames = names;

otherNames.push("Sam");

console.log(names.length);
C#
var names = new List<string> { "Ada", "Lin" };
var otherNames = names;

otherNames.Add("Sam");

Console.WriteLine(names.Count);
Predict

What is the original collection's size in each language? Did assignment copy the elements?

Try a change → Create a separate collection before adding Sam, so the original size stays at two.

Give me a hint

Look at array spread in JavaScript and new List<string>(names) in C#. Think about the difference between copying a reference and creating a collection.

Reveal the explanation

Both: 3

Both variables refer to the same collection. C# List<T> is a reference type. By contrast, assigning a simple value such as an int copies that value.

JavaScript const stops rebinding the variable; it does not freeze the array. Creating a new collection separates its membership, but does not automatically deep-copy mutable elements. Exercise 10 explores that boundary.

Want to go deeper?

Trace which variables share an instance before thinking about copying.

05 / ENCAPSULATION8 min · Sessions 1–2

Readable outside. Changeable inside.

Properties can expose state without allowing every caller to replace it.

Node.js / JavaScript
class Counter {
  #value = 0;
  get value() { return this.#value; }
  increment() { this.#value++; }
}

const counter = new Counter();
counter.increment();
console.log(counter.value);
C#
var counter = new Counter();
counter.Increment();
Console.WriteLine(counter.Value);

class Counter
{
    public int Value { get; private set; }
    public void Increment() => Value++;
}
Predict

Both print one. Can outside code set the value to -100? Where is the boundary enforced?

Try a change → Add a reset operation that returns the counter to zero while preserving the external read-only boundary.

Give me a hint

A public operation can modify private state. A C# property can have different accessibility for its getter and setter.

Reveal the explanation

C# rejects an external assignment to Value at compile time because its setter is private. JavaScript has no setter for value; assigning it throws in strict mode, and is ignored in non-strict mode. The #value field is private.

Encapsulation lets the type control its own transitions. A private setter does not automatically enforce every business rule: inspect which operations are allowed and what each guarantees.

Want to go deeper?

Look for the difference between exposing a value and exposing a way to change it.

06 / ENUMS & INTENT5–8 min · Session 2

A choice is more than a label.

A fixed set of choices deserves a representation that expresses intent.

Node.js / JavaScript
const Mode = Object.freeze({
  Draft: "draft",
  Published: "published"
});

const mode = Mode.Draft;
console.log(mode === "Draft");
C#
Mode mode = Mode.Draft;
Console.WriteLine(mode == Mode.Draft);

enum Mode
{
    Draft,
    Published
}
Predict

Why do these comparisons produce different results? Is a member's name the same thing as its display text?

Try a change → Give the draft option a friendly display label, Work in progress, while retaining the original value for decisions.

Give me a hint

Separate presentation from identity. Investigate a small mapping or switch rather than parsing the friendly label back into an enum.

Reveal the explanation

JavaScript: false · C#: True

The JavaScript value is "draft", which differs from "Draft". Comparing against Mode.Draft avoids duplicating the literal. C# uses a distinct enum type and a declared member.

An enum is not full input validation: casting an integer such as (Mode)99 can create an unnamed enum value. Validate external input where it enters the application. Display text can change without changing the selected value.

Want to go deeper?

Keep a choice’s identity separate from its presentation, and validate external values.

07 / INTERFACES & POLYMORPHISM10 min · Session 2

Same capability, different types.

Callers can depend on behavior without knowing the concrete implementation.

Node.js / JavaScript
function describe(item) {
  return item.describe();
}

const label = {
  describe: () => "Label"
};

console.log(describe(label));
C#
IDescribable item = new Label();
Console.WriteLine(item.Describe());

interface IDescribable
{
    string Describe();
}

class Label : IDescribable
{
    public string Describe() => "Label";
}
Predict

What happens if the implementation lacks the expected method? When does each language detect it?

Try a change → Add a second implementation with different output. Call both through the same contract, without checking their concrete types.

Give me a hint

JavaScript checks the operation when it runs. C# verifies that the class fulfills the declared interface. A collection can hold values through that interface type.

Reveal the explanation

Both: Label

JavaScript's function uses whichever object provides a callable describe member. With a missing member, that call fails at runtime. In this C# example, omitting Describe from a class that declares : IDescribable causes a compilation error. Merely having a matching method does not implicitly implement the interface.

An interface supplies a capability contract; a base class can also share state and implementation. Prefer composition when the relationship is “has a collaborator”; inheritance should express a justified “is a” relationship.

Want to go deeper?

Follow the declared contract, then compare interfaces with shared implementation.

08 / LINQ TRANSFORMATIONS10 min · Session 2b

From loops to a data pipeline.

Filter, group and project. Keep the computation distinct from how you display it.

Node.js / JavaScript
const words = ["pear", "plum", "fig", "pear"];
const counts = new Map();

for (const word of words.filter(w => w.length > 3)) {
  counts.set(word, (counts.get(word) ?? 0) + 1);
}

for (const [word, count] of counts) {
  console.log(`${word}: ${count}`);
}
C#
string[] words = { "pear", "plum", "fig", "pear" };
var counts = words
    .Where(w => w.Length > 3)
    .GroupBy(w => w)
    .Select(g => new { Word = g.Key, Count = g.Count() });

foreach (var entry in counts)
    Console.WriteLine($"{entry.Word}: {entry.Count}");
Predict

Which words remain, and what are their counts? What is each C# operator responsible for?

Try a change → Display the results alphabetically. Then use an empty source and describe the output.

Give me a hint

Where filters; GroupBy creates groups; Select changes the result shape. Investigate OrderBy for ordering. An empty sequence has no groups.

Reveal the explanation

Both: pear: 2, then plum: 1 · Empty source: no lines

The C# anonymous result object holds the group's key and size. You can name intermediate steps instead of forcing every operation into one chain. The JavaScript loop is one valid implementation; it is not the only “Node.js way.”

For a “most common” result, think separately about ties and empty input. Sorting and choosing the first result silently makes a tie-breaking decision unless that behavior is intentional.

Want to go deeper?

Name the purpose of each operation before adding more operators.

09 / DEFERRED EXECUTION10 min · Session 2b

When does the work happen?

A query declaration can describe work without doing it yet.

Node.js / JavaScript
const numbers = [1, 2, 3];
const selected = numbers.filter(n => n > 1);

numbers.push(4);

console.log(selected.join(", "));
console.log(selected.join(", "));
C#
var numbers = new List<int> { 1, 2, 3 };
var selected = numbers.Where(n => n > 1);

numbers.Add(4);

Console.WriteLine(string.Join(", ", selected));
Console.WriteLine(string.Join(", ", selected));
Predict

What does each print? How often is the predicate evaluated when each result is printed twice?

Try a change → Add .ToList() immediately after C# Where(...). Add logging inside each predicate to observe timing and repetition.

Give me a hint

JavaScript array filter constructs a new array immediately. C# LINQ-to-Objects Where returns a deferred sequence. Printing through string.Join enumerates that sequence.

Reveal the explanation

JavaScript: 2, 3 twice · C#: 2, 3, 4 twice

JavaScript's predicate runs three times during filter. C#'s predicate runs four times per enumeration here, eight total. Materializing before the addition evaluates three elements once and stores the results, so the C# output becomes 2, 3 twice.

This is deferred execution, not asynchronous execution. Not all LINQ operators defer work: scalar operations such as Count() return a result immediately. Avoid side effects inside query predicates; logging here is only an observation experiment.

Want to go deeper?

Pay attention to when enumeration happens, rather than when the variable is declared.

10 / SHALLOW COPYING10 min · Sessions 1–2

A new list is not a new object graph.

A collection snapshot separates membership. Its elements may still be shared.

Node.js / JavaScript
const original = [{ name: "Ada" }];
const copy = [...original];

copy[0].name = "Lin";
copy.push({ name: "Sam" });

console.log(original[0].name);
console.log(original.length);
C#
var original = new List<Person>
    { new Person { Name = "Ada" } };
var copy = original.ToList();
copy[0].Name = "Lin";
copy.Add(new Person { Name = "Sam" });

Console.WriteLine(original[0].Name);
Console.WriteLine(original.Count);

class Person
{
    public string Name { get; set; } = "";
}
Predict

Does the original name change? Does the original collection gain a second element?

Try a change → Create new element objects while copying, so changing a copied name leaves the original name untouched.

Give me a hint

Draw two containers pointing to the same element. Then consider JavaScript map or C# Select to construct a new element per entry.

Reveal the explanation

Both: Lin, then 1

The new collection contains a copy of the reference to the original person. Mutating that person is visible through both collections. Adding another person only changes the new collection's membership.

Copying each person solves this example, but nested mutable data would introduce another boundary to consider. A read-only collection interface also does not make its elements immutable.

Want to go deeper?

Separate copying a container from copying the objects reachable through it.

11 / IDENTITY & EQUALITY10–12 min · Session 1 stretch

Equal data. Different instances.

Records add value equality without turning a record class into a value type.

Node.js / JavaScript
const first = { name: "Ada" };
const second = { name: "Ada" };

console.log(first === second);
console.log(first.name === second.name);
C#
var first = new Person("Ada");
var second = new Person("Ada");

Console.WriteLine(first == second);
Console.WriteLine(ReferenceEquals(first, second));

record Person(string Name);
Predict

Which comparisons are about identity, and which are about values? Predict all four Boolean results.

Try a change → Replace the record with a plain class exposing the same name and constructor, without custom equality. Predict what == does.

Give me a hint

The compiler generates equality members for a record. ReferenceEquals continues to ask whether two references point to the same object.

Reveal the explanation

JavaScript: false, true · C#: True, False

The C# record instances are different objects, but their string member values match. With a plain class and no custom equality, this example's == comparison becomes false.

record alone means record class: it is still a reference type. Records do not provide automatic deep immutability or recursive content equality for arbitrary collections. Also, the rule for a plain class is a default, not a universal law: types such as string define their own value equality.

Distinguish reference identity, value equality and immutability.

12 / INJECTION & LIFETIMES12–15 min · Session 3

Who owns the shared state?

Receiving a dependency and choosing how long it lives are related, but separate, decisions.

Node.js / JavaScript
function createCounter() {
  let value = 0;
  return { next: () => ++value };
}

function createPanel(counter) {
  return { show: () => console.log(counter.next()) };
}

const shared = createCounter();
const first = createPanel(shared);
const second = createPanel(shared);
first.show();
second.show();
C# / Microsoft DI
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddSingleton<Counter>();
services.AddTransient<Panel>();
using var provider = services.BuildServiceProvider();

var first = provider.GetRequiredService<Panel>();
var second = provider.GetRequiredService<Panel>();
first.Show();
second.Show();

public class Counter
{
    private int _value;
    public int Next() => ++_value;
}

public class Panel
{
    private readonly Counter _counter;
    public Panel(Counter counter) => _counter = counter;
    public void Show() => Console.WriteLine(_counter.Next());
}
Predict

What do both examples print? What changes if the C# counter registration becomes transient?

Try a change → Give each JavaScript panel a newly created counter. Make the equivalent C# lifetime change. Explain why both outputs change.

Give me a hint

The two panels are separate objects in both examples. Trace whether their counter dependencies point to one instance or two. The container constructs Panel by supplying its constructor parameter.

Reveal the explanation

Both initially: 1, then 2 · Separate counters: 1, then 1

A singleton registration reuses its instance within this provider; it is not a universal, process-wide singleton. A transient counter is created each time it is resolved to construct a panel. A transient panel can still hold the same singleton counter as another panel.

The container is composition machinery. Constructor injection also works with ordinary new calls, and it does not require an interface for every class. Services should receive the collaborators they need rather than looking them up from a provider everywhere.

A console app has no automatic HTTP request scope. Shared mutable state can justify a lifetime decision here, but reassess it if the application later becomes concurrent. This tiny counter is not thread-safe; it is only a sequential demonstration.

Trace construction and instance reuse as two separate responsibilities.
